# How sth-ui is built

sth-ui ports Mantine 9.7.4 to Foldkit. The components, their props, their named parts and their defaults follow
Mantine. The styling follows StyleX's own practice instead of Mantine's CSS modules, because every app that uses
sth-ui already compiles StyleX.

## Styling: StyleX, the way StyleX documents it

- Every style is a `stylex.create` object in the component's own file. No global CSS, no class names for other
  code to target, no descendant selectors: an element is styled only by the classes on it.
- Variants and sizes are `stylex.create` maps keyed by the prop's values (`variants.filled`, `sizes.md`), chosen in
  `stylex.props` (StyleX's Variants recipe). Mantine resolves these to CSS variables at runtime; sth-ui does not.
- Every element a component renders is `box-sizing: border-box` (from `sx`), standing in for Mantine's global
  baseline, so `w` and `p` add up the way they do in Mantine.
- Longhands only. StyleX drops `border` and `background` shorthands, and a longhand always beats a shorthand.
- Real elements instead of pseudo-elements where Mantine uses `::before` for a visible part (Button's loading veil).
- Dynamic styles (a function in `stylex.create`) only for values a person passes at runtime: a number size, a hex
  colour, a width.

## Tokens and themes

- `src/theme/palette.stylex.ts` is Mantine's palette (14 colours, 10 shades) as `defineVars`, generated by
  `tools/tokens.ts`. `src/theme/tokens.stylex.ts` holds the semantic groups: `colors` (text, body, dimmed, default,
  disabled...), `accent` (the slots a coloured component reads: filled, light, outline and their hovers),
  `space`, `radius`, `fontSize`, `lineHeight`, `fontWeight`, `shadow`, `font`, `heading`, `zIndex`.
- Light and dark live in one value, `light-dark(light, dark)`. `ThemeProvider` sets `color-scheme` to `light`,
  `dark` or `light dark` (follow the device), so forcing a scheme and following the device need no second theme.
- A theme is a StyleX theme: `stylex.createTheme(radius, { md: "12px" })` in the app's own `.stylex.ts`-adjacent
  module, passed to `ThemeProvider`'s `themes`. By default (`scope: "document"`) the provider also copies its theme
  classes (the themes, accent, base font and colours, and colour scheme, not its own style props or part styles)
  onto `<html>`, as Mantine puts its variables on `:root`, so content a Portal moves to `body` keeps the theme,
  font and colour scheme. The provider renders those classes and its scope as attributes; an always-attached
  Mount follows them with a MutationObserver, and takes the classes back off when the provider leaves or
  switches to `scope: "element"`. A provider with `scope: "element"` themes only its own
  subtree, so two parts of one page can carry different themes; use that for every provider inside another.
- Mantine's `primaryColor` and a component's `color` prop are both an accent theme: `src/theme/accents.ts` has
  `stylex.createTheme(accent, ...)` for every palette colour, generated with the palette. `ThemeProvider` takes a
  primary accent; a component with `color="red"` applies `accents.red` to its own root. A colour outside the
  palette (`#7048e8`) fills the accent slots inline through `setVars`, with hovers and tints built from `color-mix()`.
  Runtime values never use StyleX dynamic style functions: they compile to branches no test can reach.

## Style props

Every component takes Mantine's style props (`m`, `p`, `w`, `c`, `bg`, `fz`, `bd`...) on its root, as Box does.
A plain value becomes an inline style, as in Mantine. A responsive value (`{ base: "xs", sm: "xl" }`) uses
generated StyleX rules: one variable per prop per breakpoint (`src/styles/stylePropVars.stylex.ts`) and one rule
per prop with a non-overlapping media range per breakpoint (`src/styles/stylePropRules.ts`), both written by
`tools/styleProps.ts`. The value for each breakpoint is cascaded in TypeScript and every breakpoint is set, so a
child never inherits a parent's value. `bd` and `bg` are inline only (StyleX has no border or background
shorthand). Breakpoints are Mantine's em values, written as mobile-first `min-width` keys in a plain constant in
each file that uses them, not a shared `defineConsts`: an app's dev server can write CSS before it has compiled a
constants module, and every rule keyed by one then has an empty selector. StyleX's media query ordering, on by
default and on here, turns the `min-width` keys into the ranges that do not overlap; an app must not turn it off.

## Configuration that is not style

What Mantine keeps in `theme.components` besides styles stays a plain object: `createUi({ components })` gives each
component its default props and default part styles, and every component is bound to that configuration once
(`ui.Button(h, props)`). Slot order (`order` on Button, `inputWrapperOrder` on inputs) is a prop and so can be a
default too.

## The Styles API

Every component names its parts as Mantine does (`root`, `inner`, `section`, `label`, `loader` for Button) and
takes `styles: { [part]: StyleXStyles }`, applied last in `stylex.props` so a caller's style wins
deterministically. The same per-part styles can come from `createUi`'s component configuration. `attributes`
puts extra attributes on a part. `unstyled` drops the component's own styles and keeps the caller's.

## State and behaviour

Foldkit is the Elm architecture: no component state. A component that needs state (Menu, Combobox, Tabs,
Popover, Select...) builds on `@foldkit/ui`'s accessible primitive and exposes its `Model`, `Message`, `init` and
`update`, so the app's Model holds it. Plain components take values and Messages (`checked`, `onChange`).

## Components with state

Splitter is the first, and the pattern for the rest. Mantine's hook becomes three pieces the app wires up:

- The engine is pure functions in `src/hooks/` (as Mantine keeps `useSplitter` in `@mantine/hooks`), unit tested
  in the logic suite.
- The state (`Model`, `Message`, `OutMessage`, `init`, `update`) lives in the component's `model.ts`, free of
  StyleX, so the logic suite unit tests it; the component module re-exports it with its view and
  `subscriptions`. `update` returns the next model and the out messages that stand for Mantine's callbacks.
  Functions on the model stand for its imperative ref.
- The view takes `model` and `toParentMessage`. It measures itself with a `Mount` (a `ResizeObserver` started
  when the element appears), and anything that must hear the whole document (a drag) is a subscription that
  runs only while the model says so.

A subscription starts after the update that enables it, so a quick press and release can finish before it
listens: Splitter also ends a drag on the handle's own pointer-up. The drag subscription sets the body's resize
cursor and attaches its document listeners in one step, so a story waits for the cursor a person sees before it
moves the pointer. A press or key press carries the container's size measured at that moment, as Mantine
measures on demand, so input before the first resize reading still works.

A Mount must always be on its element: Foldkit takes the cleanup from the element's latest render, so a Mount
added only while a model is open never releases. Keep it attached and let it follow a data attribute
(`data-opened` on Modal) for what should only happen while open. Content a Portal moves loses focus, so first
focus waits a frame, as Mantine's timer does, and is skipped if focus is already inside the trap by then (so
an outer trap mounted a frame late never pulls focus out of an inner one). A part's `styles` may be a StyleX style or an inline `setStyle`,
as Mantine's `styles` take style objects.

Stories host one with `app` from `src/stories/harness.ts`: a small Elm app per story with its own `Model`,
`Message`, `update` and lifted subscriptions. A crash renders the failing message and the error in an `alert`,
so a failed test shows why. Drags in play functions use one `userEvent.setup()` session, so a press and its
release belong to the same pointer. A story never retries input until the app catches up: it waits for what a
person would see, then acts once. An element found by structure goes through `present` (`src/stories/dom.ts`),
so a missed lookup fails the test instead of measuring some other element.

## Testing update

Every unit test of an `update` is a foldkit Story (`foldkit/test`): given a model, send Messages, assert the model,
the out message and the pending Commands, and resolve each Command with the Message it would produce. The browser
stories above test what a person sees; Stories test the state machine underneath.

- `update` in `model.ts` returns its own Commands, defined beside it (`focus.ts`, `commands.ts`) with their own
  small message union mapped into the component's, so a Story can resolve them and the browser suite covers their
  DOM work. A component file re-exports that `update`; it never turns data into Commands itself.
- Story resolves a Command with the Message of its own definition and maps it through the parent, as the runtime
  does. A Command defined per call (form validation wrapping the caller's validator) is matched by a test
  definition of the same name.
- Story refuses a new Message while Commands are pending. To test a race (focus returning before a close delay
  ends), build the waiting model with `modelAfter` from `@sth-ui/testing/Story.ts` and send the late Message
  yourself. An `update` that returns `outMessages` goes through `listingOutMessages`.
- foldkit's own transitions, menus, popovers and comboboxes have steps that resolve their focus and animation
  Commands in `@sth-ui/core/testing/`.
- A Command's own effect (a timer, a clipboard write) is tested once directly with `TestClock`, since Story never
  runs it.

## Differences from Mantine worth knowing

- No `--mantine-*` CSS variables to override; themes override StyleX variable groups instead.
- No `classNames`, static `mantine-*` classes or `vars` props; the Styles API takes StyleX styles per part.
- `theme.scale`, `rem()` scaling and `fontSmoothing` are not ported: StyleX themes override sizes directly.
- Breakpoints are fixed at build time; `lightHidden`/`darkHidden` are not ported (light-dark() only works for colours).

## Testing at a width

Stories that depend on width set Storybook's viewport global (`globals: { viewport: { value: "phone" } }`);
the Storybook Vitest addon resizes the page to it, which Vitest's own viewport option does not do here.

## Building with StyleX

- A production build appends StyleX's CSS to a CSS file the app already ships. An app (and Storybook's preview)
  must import at least one stylesheet of its own, or the build writes `stylex.css` and nothing links it, and every
  component renders unstyled. Storybook's is `.storybook/preview.css`.
- In development the StyleX plugin collects CSS on the first request; if that request arrives before every
  module holding `defineVars` has been transformed, Lightning CSS fails with "Invalid empty selector". Vite warms
  up `src/**/*.ts` at start (`server.warmup` in `vite.config.ts`) so the first page sees every rule.
- `browserslist` (root `package.json`) targets current browsers so Lightning CSS keeps `light-dark()` native.
